## AI 使用说明

### 1) AI 在关键环节提供的帮助

1. 需求收敛与边界澄清  
   - 结合题干快速拆解“必须做/明确不做”，形成可执行的问题定义。  
   - 在“可靠投递语义、成功判定、幂等归属”这些关键边界上提供备选表达，提升文档清晰度。

2. 架构备选与 trade-off 对比  
   - 协助形成 DB 状态机方案与 CDC(binlog)+MQ 方案的并列分析。  
   - 对重试策略（固定、指数、抖动、按错误分类）给出可比较维度，便于做 MVP 取舍。

3. 从设计到代码的一致性落地  
   - 按 LLD 推进 编码落地（状态机、调度、查询、死信重投），并做编译验证。  
   - 识别并修复实现细节问题，保证方案可运行。

### 2) AI 给出但未采用的建议（及原因）

1. 在平台侧承诺更强的有序/幂等语义  
   - 未采用原因：这会让平台越过边界、侵入业务域，导致耦合上升且泛化能力下降。  
   - 最终决策：平台坚持 at-least-once，外部系统基于 `bizKey` 实现幂等和业务顺序约束。

2. 过早引入 CDC(binlog)+MQ 作为 MVP 主实现  
   - 未采用原因：在当前作业阶段，该方案的基础设施与运维复杂度高于收益，不利于快速交付可验证版本。  
   - 最终决策：MVP 先落地 DB 状态机 + 周期扫描，同时将 CDC(binlog)+MQ 作为明确演进路径。

3. 重试策略初版仅固定间隔且硬编码实现  
   - 未采用原因：可扩展性不足，后续策略演进（指数退避、抖动、按错误分类）会侵入调度主流程。  
   - 最终决策：升级为策略模式（`RetrySchedulePolicy`），并在 HLD/LLD 中补充多策略对比和 trade-off。

### 3) 自己做出的关键决策及原因

1. 语义与系统边界先行  
   - 关键决策：平台语义定为 at-least-once；成功判定以 HTTP 2xx 为准；幂等与业务顺序由外部系统基于 `bizKey` 负责。  
   - 原因：确保平台聚焦“可靠投递”主职责，避免过度承诺造成边界失控。

2. 架构层保留备选并做取舍，而非单一路径  
   - 关键决策：在设计阶段主动引入 CDC(binlog)+MQ 作为备选架构进行对比，再基于 MVP 目标选择 DB 状态机方案。  
   - 原因：既保证当前交付阶段的实现效率与稳定性，也为规模化演进提供思路方案和可扩展性。

3. 调度策略从“能跑”升级到“可演进”  
   - 关键决策：将重试能力抽象为策略模式，补齐 fixed/exponential/jitter/classifier 的比较与 trade-off。  
   - 原因：在不改状态机主流程的情况下支持后续演进，降低扩展成本和重构风险。
