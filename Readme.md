# AI使用说明
## AI在哪些关键地方提供了帮助
1. 需求分析阶段 -> 使用AI分析并拆解需求，确定系统边界，在AI对于系统边界不明确的地方人工介入确定边界
2. 方案设计阶段 -> 与AI进行交互，设计实现方案，在关键决策点上人工进行取舍，完成从HighLevelDesign
3. 编码实现阶段 -> 让AI按照LLD进行编码实现，并验证(todo)

## AI给出但没采用的建议
1. 对于消息幂等和有序，AI建议平台保证这两点 -> 平台不应该也无法保证，平台能做的是提供一个业务唯一的id，让消费者去保证这两点。
2. 对于消息持久化，AI建议用database + 本地队列来实现 -> 这种方式开发复杂度高，所以没采用，而是用database存储元信息(方便进行任务管理、追溯等) + mq中间件存储具体信息(持久化 + 投递)。
3. 对于核心架构，AI建议采用“接入层 - 核心层 - 持久化层 - 投递层 - 可观测层”水平分层架构 -> 这种分层会产生耦合，采用垂直划分的模块架构会更合理。

## 自己做出的关键决策及取舍原因
1. 明确通知投递的语义是“至少投递一次”，幂等与保序全部交给外部系统实现，平台仅提供业务唯一id作为支撑。
- 明确平台核心定位是 “可靠投递”，不深入业务逻辑，避免平台复杂度过高。
- 幂等、保序与具体业务强相关，由外部系统实现更贴合业务需求，也符合 “平台仅负责至少一次投递” 的核心目标。
2. 明确系统边界：投递成功的标志是外部HTTP接口返回"2xx"，即只关注投递成功，不关注最终是否落地。
- 平台不应该与外部系统有过多耦合，只关注消息投递这个动作本身是否成功，而不保证最终结果的落地。
3. 持久化层不采用单一的mq或者database，而是采用database + mq，用database存储消息元信息，支持任务管理和调度；用mq存储消息具体信息，支持任务执行。
- mq仅擅长消息传递和临时持久化，无法实现精细化状态管理和复杂查询；引入 database 可解决状态追溯、问题排查、重试管控的痛点，二者协同可形成可靠投递闭环，且不增加过多复杂度。
- 避免数据冗余，减少 database 数据量压力；通过任务 ID 即可实现 database 与 mq 的关联，无需重复存储消息内容，同时保证状态可追溯，逻辑更简洁。
- 利用 mq 原生能力可大幅降低开发复杂度，避免重复开发排队、重试、死信等功能，提升开发效率。
